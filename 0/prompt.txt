AIKit: extensive architecture and engineering review
Repository: Aegean-E/AIKit

Reviewed against the public GitHub repository and its current default branch, main, on October 24, 2026.
1. Executive assessment
AIKit's strongest idea is to make AI-assisted software development auditable and recoverable, rather than merely giving an AI agent a collection of prompts. Its design combines persistent task state, version-controlled operating rules, project-specific quality gates, source-code mapping, secret scanning, and verification of the actual commit.

Architecture and product concept
Promising
AIKit has a coherent answer to a real problem: AI coding agents can lose context, violate project constraints, leave incomplete work, and claim that code is ready when the tested files differ from the committed files.




Engineering discipline
Strong design intent
The repository includes unit and integration tiers, Windows/Linux CI, generated-rule consistency checks, commit verification, secret scanning, and operational dogfooding.




Current reliability
Needs investigation
The latest published CI runs are failing repeatedly. That is the most important immediate concern because a tool whose main promise is rigorous verification must itself have a demonstrably reliable verification pipeline.



The project's GitHub description summarizes it as a local-first, hash-chained audit ledger, policy review, and self-contained evidence packs. The checked-in implementation is broader: it also manages project lifecycles, developer-agent instructions, UI change boundaries, and delivery workflows. Repository and source tree.

One distinction matters throughout this review: a safeguard being implemented is not the same as proving that the safeguard is effective against every relevant failure. The assessment below evaluates the architecture, implementation evidence, and remaining proof obligations separately.
2. What the implementation actually does
AIKit is best understood as a local-first development control plane for AI coding agents, with a set of auditable workflows surrounding the code-generation process.
1. Rules and project context

GUIDELINES.md · project guidelines · architecture records


2. Agent workflow

OpenCode subagents · task ledger · checkpoints · handoff packets


3. Verification

Tests · code-structure checks · secret scans · UI proofs · operational dogfooding


4. Delivery

Commit verification · project readiness checks · explicit GitHub publishing


This is a conceptual view of the architecture documented in knowledge/architecture.md, not a claim that the entire workflow is currently enforced by GitHub.
The main subsystems
Subsystem	Implementation	Purpose
Governance	GUIDELINES.md, scripts/sync_principles.py	Generates consistent instructions for multiple AI coding environments from one source of truth.
Task persistence	scripts/disruption_recovery.py	Records checkpoints, phases, plans, task handoffs and recovery state.
Project lifecycle	scripts/project_registry.py, scripts/aikit_cli.py	Creates or attaches projects, maintains their memory and detects their toolchains.
Quality controls	scripts/project_gates.py	Resolves and runs project-specific tests and additional gates.
UI boundaries	scripts/ui_contract.py, scripts/ui_proof.py	Optionally bounds changes to declared UI surfaces, with change budgets and inventory proofs.
Security hygiene	scripts/check_secrets.py	Detects known credential patterns and certain suspicious secret assignments.
Commit verification	scripts/verify_commit.py	Checks a commit in an isolated Git worktree rather than trusting only the current working tree.
Operational verification	scripts/dogfood.py	Exercises the CLI in a disposable environment, including failure scenarios.

The most valuable architectural decision: one source of truth
AIKit keeps its human-maintained rules in GUIDELINES.md and generates multiple agent-facing instruction files from them. It also maintains an AST-derived codebase map and checks whether generated files have drifted.

This addresses a practical failure mode in multi-agent development: the same rule gets copied into several instruction files, then one copy changes while the others remain stale.

The design is stronger than simply maintaining a collection of prompts because it couples the documentation to automated checks. However, it still has a limit: generated instructions and static gates can constrain an agent's workflow, but they cannot guarantee that a model will follow every rule or that the checks cover every important behavior.
The task ledger: what is implemented versus what is claimed
There is a significant discrepancy between the repository description and the current implementation.

The GitHub description advertises a hash-chained ledger, tamper-evident audit evidence, and self-contained evidence packs. In contrast, scripts/disruption_recovery.py and knowledge/data_models.md describe a versioned JSON ledger containing an active task and checkpoints. Its writes use a lock, a temporary file, fsync, atomic replacement and a backup.

Those are useful crash-resilience mechanisms. They are not, by themselves, cryptographic tamper detection.

In the current tree, I could not find a hash-chain implementation for ledger entries or a feature that exports self-contained evidence packs. The SHA-256 usage I found relates to UI-contract digests and the dogfood fingerprint, not a hash chain over the task ledger.

This is the most consequential product-definition issue I found. There are two sound ways to address it: implement and test the advertised audit-evidence features, or revise the repository description so it accurately describes the crash-resilient development ledger that already exists.
3. Engineering strengths
A. Persistence and recovery are unusually well developed
The task ledger is not just a text file that an agent overwrites. disruption_recovery.py implements several concrete safeguards:
- A lock around read-modify-write operations to reduce lost updates when agents work concurrently.
- Temporary-file writes followed by flushing, fsync and atomic replacement.
- Backup and recovery handling for corrupt or incompatible ledger state.
- Schema-version validation and bounded checkpoint history.
- Explicit task phases, impact assessments and handoff packets for interrupted work.
This is a sensible response to real failure modes: an agent session can disappear, a machine can crash, or two workers can update shared state concurrently.

The design also distinguishes recoverability from task completion. Completing a task requires identifying the active task, and switching to a different in-progress task is recorded rather than silently erasing the previous task.

Assessment: strong foundation for crash-resilient agent workflows.

One limitation remains: atomic persistence protects against many accidental failures, but it is neither a cryptographic integrity mechanism nor a complete transactional system. A user or process with write access can still alter a plain JSON ledger.
B. Commit-level verification is an excellent design choice
verify_commit.py addresses a subtle but important problem: the working tree can be tested successfully even though the actual Git commit contains less than the code that was tested.

AIKit checks out the selected commit into a temporary Git worktree and runs its gate suite there. This is a better guarantee than simply trusting that the latest test run corresponds to the staged files.

The script also attempts to distinguish an unpushed commit from one already published before recommending recovery actions. That helps avoid destructive advice such as resetting a commit that has already reached a remote.

This design is valuable even beyond AI development. It would be useful in any automated code-generation or release pipeline.
C. The test architecture is substantial
The repository has two dedicated test modules:
- tests/test_kit.py: 467 test methods by source inspection, covering rule generation, schemas, recovery, source structure, concurrency-related contracts and other internal mechanisms.
- tests/test_integration.py: 57 test methods, including real CLI execution, project lifecycle workflows, Git behavior, UI contracts and publishing.
That is 524 test methods by my count. The unit tier also guards against spawning subprocesses, while the integration tier is specifically intended to exercise real process behavior. That separation is a good engineering practice.

The custom reachability check is another thoughtful addition. It attempts to detect capabilities that are implemented and tested but never called from production code, as well as persisted-state keys that are read or written inconsistently.

Two caveats matter:

First, these tests do not constitute 100% code coverage. The README's requirement for a 100% test pass rate means that the suite must pass; the repository does not thereby establish that every behavior or branch has been tested.

Second, some tests are necessarily coupled to implementation conventions and documentation structure. That is appropriate for generated-rule consistency, but it can make refactoring more expensive if internal architecture changes without changing observable behavior.
D. Per-project isolation is a strong product decision
AIKit's project model separates the AIKit repository from the projects it manages. A project gets its own Git repository and .aikit/ directory, including its configuration, guidelines, decisions and task state.

This prevents a project's files from accidentally becoming part of AIKit's own codebase map or ledger. It also gives each project a separate set of test commands and configurable gates.

The project_gates.py design is reasonably extensible: it detects relevant checks from supported project configurations, allows project-specific additions, and keeps the built-in hygiene, guidelines and secret checks non-overridable.

For a cross-language development workbench, that is a useful foundation.
E. Portability and low setup cost are genuine advantages
AIKit targets Python 3.10+ and uses the Python standard library for its core. It does not require a Python dependency installation just to run the basic checks.

The CI workflow is designed to exercise both Ubuntu and Windows under Python 3.10 and 3.13. Cross-platform behavior is especially relevant for file locks, path handling, shell quoting, Unicode paths and filesystem durability.

The code also explicitly supervises processes, sets timeouts, and attempts to terminate process trees. These are substantive operational safeguards, rather than cosmetic features.

The trade-off is that optional capabilities still depend on external programs: GitHub publishing needs the GitHub CLI, and subagent delegation needs OpenCode and an available model provider.

4. Highest-priority findings
Priority reflects what I would fix before treating AIKit as a dependable public release, not a formal security audit rating.

Finding 1 — Hosted CI is not providing usable verification evidence
Release blocker
The latest GitHub Actions run failed on October 24, 2026. All four matrix jobs finished within approximately two seconds, and the public job metadata showed neither a runner name nor any recorded steps.

This is consistent with a runner or workflow-startup failure, not proof that the test suite itself failed. The exact infrastructure cause was not exposed by the metadata I could retrieve.

Action: investigate why jobs are failing before executing steps. Then obtain a successful end-to-end run covering every matrix cell before presenting the hosted CI as evidence of reliability.




Finding 2 — The verification pipeline is not enforced at the GitHub branch level

The public branch metadata reports main as unprotected. The latest failed workflow also did not prevent additional commits from landing on the branch.

AIKit's rules describe a disciplined verification process, but a local script and a GitHub Actions workflow do not automatically prevent an authorized contributor or agent from pushing an unverified commit.

Action: establish branch protection or a repository ruleset requiring successful CI before merging or updating the release branch. A required check is useful only once it is reliably running.




Finding 3 — The published product description overstates the current audit implementation

The difference between the advertised hash-chained audit ledger and the implemented JSON task ledger is discussed above. I could not locate a ledger hash chain or self-contained evidence-pack exporter in the current source tree.

This is more than a naming issue. Buyers and developers evaluating AI governance tools may interpret “tamper-evident” as a cryptographic property.

Action: either implement verifiable, append-only audit evidence with a clearly defined trust model, or reposition the product around the safeguards that already exist.




Finding 4 — new --publish bypasses the normal publishing preflight

cmd_new calls the lower-level publish_project() function directly when --publish is supplied. By contrast, cmd_publish() first checks project readiness, executes the gates and refuses publishing if no test gate exists.

The current task ledger also records the discrepancy as an unresolved design question.

The immediate practical consequence is inconsistent behavior: creating and publishing a new project does not have the same preconditions as publishing that project afterward.

Action: extract a shared publishing preflight and decide whether new --publish must follow it, or explicitly define it as an exception for publishing a starter scaffold. Add a regression test for the chosen contract.




Finding 5 — Configurable quality gates are not a security sandbox

AIKit deliberately executes project-defined test commands and additional shell gates. These commands run under the user's operating-system account. Process supervision and timeouts constrain execution, but do not prevent a command from accessing files or resources that the account can access.

That is normal for a local developer tool, but it should be explicit: attaching an untrusted repository and running its configured gates can execute untrusted code.

Action: document the trust boundary, never describe ordinary gate execution as OS-level isolation, and consider optional containerized execution for untrusted projects. Keep the existing disposable dogfood environment clearly distinguished from that stronger form of sandboxing.



5. Security and evidence quality
Secret detection is useful, but it is not a complete security scanner
check_secrets.py uses recognizable patterns for known vendor credentials and an entropy heuristic for suspicious assignment-shaped lines. It also scans relevant Git diffs and can inspect commit ranges to catch credentials that were introduced and subsequently deleted from the working tree.

That is a good defensive baseline, especially given that agent memory can itself become committed content.

However, a pattern-based scanner cannot guarantee detection of every secret. Credentials with unfamiliar formats, unusual encodings, embedded binary data or unrecognized token structures can evade detection. Conversely, an explicit allowlist can intentionally suppress a finding.

For releases that make security claims, I would add an optional dedicated secret-scanning tool and test the combined scanner against a representative corpus of true positives and false positives. I would also document exactly which files and Git states each scan mode covers.
Static architecture checks need to be presented as heuristics
The reachability checker and code-structure audits are useful because they automate checks that are easy to forget. But AST-based analysis cannot reliably understand every dynamic call, reflection-based dispatch mechanism or runtime plugin registration.

Consequently, a clean reachability report is evidence that the checker found no violation under its analysis model. It is not a mathematical proof that every capability is used correctly.

The same principle applies to the UI contract. Its surface restrictions, change budgets, textual snapshot inventory and style checks can prevent certain unintended edits. They are not a substitute for real browser testing or visual regression testing unless the project supplies appropriate proof commands and those commands actually exercise the rendered interface.
“Universal” cross-model behavior has not been established empirically
The repository's principles_audit_ledger.md explicitly describes its cross-model behavior predictions as predictions rather than measurements. It says no model was run against the principles for that audit.

That is an honest caveat, and it should remain visible.

The code does establish useful mechanical properties: generation consistency, schema validity, workflow contracts and selected operational behaviors. It does not yet establish that GPT, Claude, Gemini and other coding agents interpret the same rules identically or produce equivalent results.

Recommended experiment: define a common task corpus, run the same tasks through several agent hosts and models, and measure rule violations, test success, recovery success, unintended file changes and delivery-gate bypasses. Publish the protocol and results. That would convert an important part of the project's “universal” proposition into an empirical claim.

6. Maintainability, packaging and adoption
The repository is unusually rich in documentation for its current maturity. At the time of review, its knowledge/decisions.md file is approximately 467 KB, and the most recent commit messages refer to ADR-195. The repository itself was created on October 15, 2026, and currently has five stars, no forks and no published releases.

Those numbers do not establish poor code quality. They do mean there is little public adoption evidence so far, and the very large decision register could become a maintenance burden.

I would preserve decision history, while making it easier to navigate. Stable architecture decisions belong in the ADR register; detailed per-change verification records can live in a more compact engineering log or machine-readable report. The existing generated code map and knowledge index are useful foundations for this separation.

The project is also a source-based CLI rather than an installable Python package. There is no pyproject.toml or conventional package metadata in the current top-level tree. That is consistent with its zero-dependency, copy-into-a-project philosophy, but it limits how easily users can install and version it as a reusable development tool.

Before broader adoption, I would add a versioned release, a short first-run demo, a migration policy for project-local .aikit/ state, and clear compatibility guarantees for persisted schemas. The current README has extensive operational instructions; a new user should not need to understand all 20 principles to complete their first successful project workflow.

8. Recommended implementation roadmap
1

Restore verifiable CI and enforce it

Identify why GitHub Actions cannot start its jobs. Get a successful run across the four supported OS/Python combinations, then require that check on the release branch. This establishes the minimum credible development loop.


2

Resolve the audit-ledger product definition

If tamper-evident evidence is the intended product, implement it as a distinct, testable subsystem. A sound starting point is a canonical event format, monotonically increasing sequence numbers, hashes linked to previous entries, and a verifier that rejects modified or reordered history.

For meaningful tamper evidence, also define how a trusted checkpoint is preserved. A hash chain alone cannot stop a privileged attacker from rewriting the entire ledger and recomputing every hash. Signed manifests, independently retained checkpoints or a trusted remote anchor can provide the missing trust boundary.


3

Unify the delivery contract

Route every publishing entry point through the same readiness and gate checks, unless a documented exception is intentional. Test that a failing gate, missing test command, open UI task or secret finding blocks the relevant publishing path.


4

Build a demonstrable evidence workflow

For each verified run, record the exact commit SHA, commands executed, tool versions, exit codes, test results and relevant policy version. Export a self-contained manifest, verify its hashes, and clearly distinguish automated evidence from human review or claims that were not tested.


5

Prove behavior across models and make adoption easier

Publish a reproducible multi-model evaluation, a one-minute end-to-end demo and a versioned release. Make the quick start lead with one concrete workflow: create a project, record a checkpoint, simulate interruption, resume, run gates and show why a noncompliant change cannot be published.



9. Commercialization implications
For the commercial dual-licensing path you have been considering, the AGPL-3.0 license is compatible with a model in which the public core is available under AGPL and customers can obtain a separately negotiated commercial license. That strategy depends on the licensor having sufficient rights to offer the alternative license; contribution ownership and licensing terms therefore need attention before accepting substantial outside contributions.

The more immediate product issue is differentiation. A generic collection of prompts, project scaffolding and test gates is useful, but the claimed audit-evidence capability could be a much stronger reason for organizations to pay. Verified, tamper-evident evidence packs, policy evaluation and repeatable compliance reporting would provide a clearer enterprise proposition than documentation alone.

I would not build a large premium layer yet. First make the core claims demonstrably true and the release pipeline trustworthy. Then validate whether developers actually value the evidence artifact enough to adopt it.
Final verdict
AIKit is a promising engineering prototype with real substance in persistence, recovery, project isolation and verification. It is more sophisticated than a prompt bundle, and several of its mechanisms address failures that conventional AI coding workflows do not handle particularly well.

Its current limitation is not a lack of features. It is the gap between an extensive set of internal safeguards and an externally verifiable product promise. The hosted CI is not currently yielding test evidence, the branch is not protected, and the headline cryptographic audit claims are not reflected in the ledger implementation I inspected.

I would prioritize fixing those issues over adding further governance rules or expanding the documentation. Once the CI is green, the product description matches the code, and the audit evidence can be independently verified, AIKit will have a much stronger foundation for a public release, an open-source showcase or a commercial product.
